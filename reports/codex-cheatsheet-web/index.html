首次进入

系统可能让你选择用途（日常工作、开发、学习）。随便选一个接近的即可，后面可以改。

界面通常分成三块，新手先记住三件事：

左侧：任务管理区

新对话、搜索、插件、自动化、项目、历史线程等入口。

中间：对话交互区

你在这里输入需求、批准权限、查看 Codex 的过程说明。

右侧：结果和侧边栏区

展示文件、网页预览、文档、PPT、表格、代码 diff、运行结果等。

新手策略

打开陌生界面后，直接对 Codex 说：

提示词
请介绍当前界面里我最常用的 5 个入口，并告诉我分别什么时候用。

Codex 里的"项目"基本对应你电脑上的一个文件夹。选中文件夹后，里面的文件就变成 Codex 的工作上下文。

标准操作

首次进入项目的推荐话术
请进入这个项目，先不要修改文件。先读一下目录结构，告诉我这个项目是做什么的、核心文件在哪里、下一步应该看什么。

项目不等于代码仓库，写作、资料整理、视频素材、运营文档都可以建项目。

权限模式行为风险推荐
默认权限只能读写所选文件夹内文件，外部/敏感操作需请示低可用
自动审查低风险自动执行，高风险再申请中新手首选
完全访问可在电脑上执行更广泛操作高谨慎使用

涉及删除、大范围移动文件、安装系统级工具、改环境变量、访问隐私目录时，仍然要认真看权限说明。

新手不要一上来就"帮我写个大项目"。选一个低风险、可验证的小任务：

  • 整理一个文件夹里的 Markdown，生成索引
  • 检查 README 是否过期，列出问题
  • 把会议记录按主题分类汇总

验收标准

任务完成后，检查实际产物：文件是否生成、内容是否正确、格式是否符合预期。不要只看 Codex 的"完成"说明。

标准操作 SOP 库

按任务场景整理的标准流程。每个 SOP 包含：适用场景、标准步骤、推荐提示词、验收方式、风险提醒。

适用场景 首次接触一个项目，或让 Codex 在修改前理解全貌。

锁定范围

确保 Codex 已进入正确的项目文件夹。

发出"只读"指令

推荐提示词
请先不要修改任何文件。读取当前项目结构，告诉我：
1. 这个项目是做什么的；
2. 核心目录和关键文件；
3. 运行、测试、构建命令；
4. 你建议我从哪里开始。

确认理解

让 Codex 复述它理解的项目目标、技术栈和关键路径，确保没有误解。

再进入修改阶段

确认理解无误后，再给出具体的修改需求。每次都先让 Codex 列出会影响哪些文件。

禁止一上来就"帮我重构"

验收方式：Codex 能准确描述项目结构、技术栈、入口文件和构建命令。

适用场景 整理 Markdown、会议记录、视频素材、运营文档等。

先扫描，不动原文件

让 Codex 先列出文件夹内容、文件数量、格式分布，给出整理方案。

明确输出位置

要求 Codex 保留原始文件不动，输出到新位置或新文件。

推荐提示词
请整理这个文件夹里的资料，生成一份结构化 Markdown。要求：
1. 不遗漏任何独特知识点；
2. 重复内容合并；
3. 冲突信息标出来；
4. 保留来源文件名；
5. 输出一份正式稿和一份整理报告。

视频素材的特殊处理

Codex 可以先统计文件数量，抽关键帧，拼成缩略图判断内容，再按规则重命名。记得要求"先给方案，等我确认后再执行"。

验收方式：原始文件未被改动，输出文件结构清晰、内容完整、无遗漏。

适用场景 安装开发工具、配置环境、验证版本。

三步原则

好的命令行任务必须满足：先检查现状 → 缺什么再安装 → 安装后验证结果。

标准提示词

推荐提示词
请检查当前电脑是否已具备完成这个项目所需环境。先列出现状和缺失项，再给安装计划。涉及系统级修改、管理员权限、删除文件、修改 shell 配置前必须问我。安装完成后验证版本和最小运行示例。

安装 Agent IDE（推荐）

建议安装 Cursor 作为 Codex 的外部编辑器。Codex 负责理解、修改、运行、验证；Cursor 负责精细编辑和人工检查。

安装并配置 Cursor
请检查我是否已安装 Cursor；若未安装，请帮我安装。安装后，把 Codex 桌面端右上角"打开编辑器"的目标设置为 Cursor，并验证是否生效。

安装不知名工具

如果工具不够知名，给官方链接，让 Codex 只根据官方文档安装，避免撞到同名不相关仓库。

验收方式：安装后运行 `xxx --version` 或最小示例，确认可用。

适用场景 让 Codex 修改代码、更新文档、实现新功能。

标准提示词
请实现这个需求：<需求>。
要求：
1. 先阅读相关文件、调用方和测试；
2. 给出简短方案；
3. 只改必要文件；
4. 改完运行相关测试或最小验证；
5. 最后说明改了什么、验证了什么、还有什么没验证。

关键原则

  • 先让它列出会影响的文件，再执行
  • 要求只改必要文件，不要"顺便优化"
  • 改完必须跑测试或最小验证
  • 让它说明"还有什么没验证"

验收方式：代码通过测试，或最小验证通过；改动范围与预期一致。

适用场景 对话变长、Codex 开始遗忘前面的约定、任务阶段切换。

查看上下文状态

界面里的小圆圈或上下文入口能看到：当前已用比例、已用/总 token 数、是否已经压缩过。

手动压缩时机

  • 一个阶段结束，要开始新阶段
  • 对话很长，Codex 开始反复遗漏前面约定
  • 已经生成了关键文件，不需要保留每个中间过程

压缩前保存关键信息

压缩前提示词
请先把当前任务的关键决策、文件路径、未完成事项、验证结果整理成一段 compact summary，然后再压缩上下文。

执行压缩

输入 /压缩 斜杠命令，或让 Codex 执行压缩。

适用场景 控制额度消耗、在速度和智能之间做选择。

任务类型推荐设置
普通整理、改文案、查文件标准速度，中等智能
大型重构、复杂排错、架构设计、跨文件修改高智能
赶时间且任务明确快速模式（额度消耗更高）
不确定时先用默认模型，出问题再提高智能程度

省额度核心方法

  • 先让它读目录并给计划，再改
  • 先让它列出影响文件，再执行
  • 先让它跑最小验证，再做大范围任务
  • 图片、视频、大文件处理前先抽样

查看额度：左下角设置里找"剩余额度"，或在对话框输入斜杠命令找"状态"。

适用场景 让 Codex 长期记住你的偏好和项目规则。

三种记忆方式对比

类型作用范围适合写什么入口

项目级 AGENTS.md 生成方法

生成项目 AGENTS.md
请阅读当前项目结构和 README，生成一份项目级 AGENTS.md。内容包括项目目标、目录说明、运行命令、测试命令、代码风格、禁止修改的路径、交付前验证要求。先给草稿，等我确认后再写入文件。

最佳实践

  • 明确、稳定、重要的规则，优先写进 AGENTS.md
  • 不要只靠自动记忆，它可能记不全
  • 共享知识库（纯文本文件夹）比锁在某个线程里更稳

适用场景 从零做网站、重构项目、整理几十份资料、做 PPT、写自动化工作流。

打开计划模式

复杂任务不要直接执行。推荐流程：选项目文件夹 → 打开计划模式 → 描述目标 → 回答关键问题 → 检查计划 → 补充约束 → 执行 → 中途干预 → 验收。

任务干预

执行中途可以直接补充指令。Codex 不会立即打断当前工具调用，但会在下次合适节点吸收。

干预示例
刚才的视觉方向太商务了，请改成更像独立创作者主页，减少营销感。

任务排队

排队示例
等当前页面做好后，请启动本地预览，截图检查移动端和桌面端，再修明显布局问题。

适用场景 沉淀重复工作流、连接外部工具、定时任务、长期目标追踪。

先跑通真实流程

沉淀 Skill

MCP 安装流程

  1. 给官方链接
  2. 让 Codex 阅读 README
  3. 让它说明权限和风险
  4. 安装
  5. 重启或授权
  6. 在设置里确认 MCP 服务器状态
  7. 做一个最小调用测试

自动化创建要点

  • 什么时候运行
  • 在哪个项目或文件夹运行
  • 使用什么输入源
  • 产出什么格式
  • 是否允许发布、发消息、改线上内容
  • 失败时怎么报告
新手建议自动化只"生成草稿"和"提醒确认"，不要自动发布/发送/改生产环境

Goals 标准写法

好的 Goal 示例
把这个 Python 工具迁移到 Rust。完成标准：所有现有单元测试通过；CLI 参数兼容旧版本；README 更新迁移说明；性能基准不低于旧版本。每完成一个阶段报告一次，不要删除旧实现，直到我确认。

问题排查中心

以"我遇到了什么问题"为入口。每个问题包含：现象、优先检查项、标准处理步骤、推荐提示词、风险提醒。

现象：Codex 给出的项目理解有误，或找不到入口文件、构建命令。

优先检查项

  • 项目里是否有 README？是否包含运行/构建命令？
  • package.json / pyproject.toml / Cargo.toml 等配置文件是否存在？
  • Codex 是否真的读了全部关键文件？

标准处理步骤

让 Codex 重新扫描

推荐提示词
请重新读取项目根目录下的 README 和所有配置文件（package.json / pyproject.toml 等），列出：1）项目类型和用途；2）安装依赖的命令；3）启动/构建/测试命令；4）入口文件位置。如果有任何信息缺失，明确告诉我。

补全信息

手动告诉 Codex 正确的入口、命令或特殊构建流程。

写入 AGENTS.md

把确认后的项目信息写入项目级 AGENTS.md，避免下次重复解释。

现象：你只想改一个功能，Codex 却计划修改十几个文件，甚至重构整个项目。

标准处理步骤

限制改动范围
请只修改实现这个需求所必需的文件。先列出你计划改动的文件清单和每个文件的改动原因，等我确认后再执行。不要重构无关代码。
  • 明确要求"先列出影响文件，再执行"
  • 指定"只改必要文件，不要顺便优化"
  • 如果已跑偏，用 Fork 回到之前的好节点

现象：Codex 弹出一个权限申请，你不确定批准是否安全。

标准处理步骤

不要立即批准

让它解释命令用途、影响路径、回滚方案。

要求解释

推荐提示词
请解释这个权限申请的具体用途、会影响哪些文件/目录、如果不批准有什么替代方案、执行后如何回滚。

高风险操作必须人工确认

删除、覆盖、发布、付款、发消息、改生产环境、系统级修改，必须看清楚再批。

现象：Codex 尝试安装工具但报错，或装完后不可用。

优先检查项

  • 网络是否正常？（部分地区需代理）
  • 是否已有冲突版本？
  • 是否需要管理员权限？
  • 安装路径是否在环境变量中？

标准处理步骤

排查安装失败
安装失败了。请分析报错信息，判断是网络、权限、版本冲突还是路径问题。给出明确的修复步骤，修复后再次验证安装是否成功。

现象：Codex 开始反复遗漏前面约定，或提示上下文接近上限。

标准处理步骤

保存关键信息

保存后压缩

执行压缩

输入 /压缩 或让 Codex 压缩上下文。

长期信息写入 AGENTS.md

重要的规则、约定、项目信息不要只靠上下文，写进 AGENTS.md 更稳。

现象：额度在短时间内大幅下降，或 Codex 反复做无用功。

标准处理步骤

  • 先让它读目录并给计划，再改
  • 先让它列出影响文件，再执行
  • 先让它跑最小验证，再做大范围任务
  • 图片、视频、大文件处理前先抽样
  • 避免在同一个跑偏的线程里死磕，用 Fork 分支
  • 不需要保留的中间过程，及时压缩上下文

现象：侧边栏预览空白、端口冲突、Browser 插件无法打开页面。

优先检查项

  • 本地服务器是否真的启动了？
  • 端口是否被占用？
  • 文件路径是否正确？
  • 浏览器插件是否已安装并启用？
排查预览问题
网页预览不工作。请检查：1）本地服务器状态；2）端口占用情况；3）文件路径是否正确；4）Browser 插件状态。给出具体原因和修复步骤。

核心区别：Skill = 怎么做（流程模板）；MCP = 连什么（外部接口）；自动化 = 什么时候做（定时触发）；Goals = 做到什么程度（完成标准）。

现象：担心自动化任务自动发布内容、发送消息、修改生产环境。

安全模板

安全的自动化创建方式
请创建一个自动化任务：<频率和时间>，在 <项目/目录> 中执行 <任务>。输出 <格式> 到 <位置>。只生成草稿，不自动发布或发送。失败时在当前线程报告原因和下一步建议。

安全原则

  • 自动化只"生成草稿"和"提醒确认"
  • 不要一开始就自动发布、自动发送、自动改生产环境
  • 明确失败时的报告方式和位置
  • 定期检查自动化任务的执行记录

最佳实践与安全边界

权限选择、人工确认清单、好任务描述结构、验收标准、流程沉淀方法。

首选：自动审查 减少频繁打断，又不会把危险操作完全放开。

涉及以下操作时，仍然要认真看权限说明：

  • 删除文件或大范围移动文件
  • 安装系统级工具或改环境变量
  • 访问隐私目录（下载、文档、钥匙串等）
  • 修改 shell 配置文件（.bashrc / .zshrc 等）
动作风险确认要点
删除文件/目录数据丢失确认路径、是否有备份
覆盖已有文件丢失旧版本确认是否可覆盖、是否需备份
发布/部署影响线上用户确认目标环境、回滚方案
付款/订阅财务损失永远不要批准
发送消息/邮件对外沟通风险确认收件人、内容、时机
改生产环境服务中断确认变更窗口、回滚方案
系统级修改系统不稳定确认影响范围、是否有替代方案

一个有效的任务描述应该包含四个部分：

目标（Goal）

你要完成什么。用一句话说清楚最终产物是什么。

❌ "帮我看看这个代码" → ✅ "把这个函数的报错处理改成返回 Result 类型"

上下文（Context）

相关文件、技术栈、约束条件。让 Codex 知道在哪里工作。

边界（Boundary）

不要做什么、只改哪些文件、不改哪些文件、不允许的行为。

验收标准（Acceptance）

怎么算完成？测试通过？预览正常？文档更新？

任务类型验收方式
代码修改跑测试、最小验证、检查 diff
网页制作本地预览、检查移动端、检查交互
文档整理查结构完整性、样本抽查、来源追溯
数据处理看样本、统计行数/字段、抽查异常值
环境安装版本验证、最小示例运行

核心原则：不要只看 Codex 说"完成了"，要看实际产物。

一次有效执行

先确保流程在真实任务中跑通了。

提取通用部分

去掉项目特有内容，保留可复用的步骤、标准、提示词。

选择沉淀形式

形式适合
AGENTS.md项目级规则、长期约束
Skill可复用工作流、固定输出格式
自动化定时触发、例行任务

验证沉淀效果

在新项目或新线程中测试，确认 Codex 能按沉淀的规则正确执行。

7 天练习路线

可执行训练计划。每天包含：目标、操作、推荐提示词、完成标准。

1
熟悉界面和项目
目标：会打开 Codex、会创建/进入项目、会让 Codex 只读分析。
推荐提示词
请介绍当前 Codex 界面，告诉我新手最常用的入口。然后读取当前项目，不修改文件，只输出项目说明。

完成标准：能说出左侧/中间/右侧三个区域的主要功能；Codex 正确描述了项目结构和用途。

2
整理一个文件夹
目标：掌握文件整理 SOP，学会要求"保留原文件不动"。
推荐提示词
请整理这个文件夹里的所有 Markdown，生成索引、主题分类和待办清单。保留原文件不动。

完成标准：原文件未被修改，输出文件结构清晰、分类合理、无遗漏。

3
安装一个工具
目标：掌握环境检查 → 安装 → 验证的三步流程。
推荐提示词
请检查并安装 GitHub CLI，安装后验证版本，并告诉我怎么登录。

完成标准：gh --version 返回正确版本号；知道下一步登录命令。

4
做一个静态网页
目标：掌握计划模式、本地预览、移动端检查。
推荐提示词
请从零做一个个人主页，先问我必要问题，再生成计划，确认后实施。完成后在侧边栏预览并修布局。

完成标准：网页在侧边栏预览正常；桌面端和移动端布局无明显问题。

5
写项目 AGENTS.md
目标：掌握让 Codex 理解项目规则并长期记住。
推荐提示词
请根据当前项目生成 AGENTS.md 草稿，包含项目说明、命令、风格、禁区、验证要求。先不要写入，等我确认。

完成标准：AGENTS.md 草稿包含项目目标、目录说明、运行命令、代码风格、禁止修改路径、验证要求；你确认后写入文件。

6
安装或创建一个 Skill
目标：掌握 Skill 的安装和创建流程。
推荐提示词
请把我整理资料的流程沉淀为一个 Skill，要求以后输入一个资料文件夹，就能输出正式稿和整理报告。

完成标准：Skill 草稿包含触发场景、输入要求、执行步骤、质量标准、输出格式、失败处理；能用最小示例验证触发。

7
创建一个低风险自动化
目标：掌握自动化创建，理解安全边界。
推荐提示词
请创建一个每周一上午 9 点运行的自动化任务：整理本项目过去一周新增 Markdown，生成周报草稿，保存到 reports/drafts，不自动发布。

完成标准：自动化任务配置完成；明确包含频率、项目、任务、输出格式、位置；设置了"只生成草稿，不自动发布"；你知道在哪里查看执行记录。

  • 给上下文：让 Codex 先读项目、列计划、确认范围
  • 给目标：描述清楚要做什么、不做什么
  • 授权工具：理解权限申请，知道什么该批什么不该批
  • 检查计划：复杂任务用计划模式，中途能干预
  • 验收产物：看实际文件/预览/测试，不看"完成"说明
  • 沉淀流程：把成功经验写成 AGENTS.md、Skill 或自动化

这就是从"问 AI"到"管 Agent"的关键转变。
