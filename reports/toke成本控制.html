01

先把账单看明白

真正决定账单的不是你敲进去的几十个字，而是系统为了让模型融入上下文自动带上的一大坨东西。

总成本 ≈ 固定前缀 + 会话历史 + 运行时检索 + 工具往返 + 模型输出
固定前缀 = System Prompt + Skill 定义 + Tool / MCP 定义 + 稳定背景文档。你的提问往往只是最后一撮“点火器”。

M1“它记得”是幻觉

  • 大模型本身无状态，“记得”其实是 Agent 层每轮把历史重新拼装再传入
  • 所谓记忆 ≈ 再次传入，不是存储在模型里

M2会话越长，每轮越贵

  • 历史不是“放着等模型想”，而是很可能每轮都重新携带
  • 越长会话 = 越重负债

M3工具调用形成回路

  • 读上下文 → 调工具 → 返回结果又塞回上下文 → 再下一轮
  • 一次任务是一连串“请求—返回—再请求”的链条
成本类型它是什么为什么放大
输入 Token系统提示、历史消息、代码片段、检索结果、工具定义每轮可能重复携带，是最大头
输出 Token模型最终回答的文字回答越长、越啰嗦、越容易失控
推理 Tokenthinking budget / reasoning effort简单任务走高推理档位会明显溢价
工具往返工具描述、调用参数、返回结果进入上下文一次工具调用常常比原问题还长
重试成本第一次做错后重新来一轮每修一次，整包上下文再付一遍

容易被低估的两项

工具往返：你以为只是“让它查个文件”，模型经历的却是 理解工具定义 → 生成参数 → 接收返回值 → 再思考，多段上下文交换。

重试成本：格式不对、结构错、找错文件——于是又来一轮：重新描述 → 附带历史 → 拉代码 → 再跑。减少重试本身就是最硬的成本优化。

认知结论： Token 优化的重点，不是把提示词写短，
而是把前缀写稳——让它能被 Prompt Cache 命中、被按需加载。
02

使用习惯：最便宜，收益最大

零工程投入，今天就能改。这一层解决“无意义的历史和废 Token”。

H1一个 Session 一件事

聊天与任务都分开：修 Bug 开一个，写文档开一个。Session 越长，继承的历史越多，每一轮越贵。

H2长会话及时 /compact

完整试错过程不是资产。需要的是：现在干什么、做完了什么、哪条路不通、下一步怎么做。

H3聊天记录不是数据库

背景、决策、约束、待办外置到文档、Memory、Repo Map、任务清单。会话只承载当前工作状态。

H4指定输出格式

「直接给结论，不要复述问题」。一行约束同时省输出，又能更可用 → 重试更少。

H5Skill ≠ 免费能力

每个 Skill 带 Description / Instructions / Examples。高频稳定通用的常驻；低频长说明的按需触发。

H6MCP 宁少勿堆

每多一个 MCP 就多一份 Tool Def + 选择成本。高频可能就两三个；工具越多决策越慢、错误调用越易发。

H7CLI 优先于 MCP

能 CLI 就 CLI（git diff / kubectl / docker ps）。MCP 的价值在跨系统编排、结构化返回、权限收敛。已有成熟命令链路时，别为看起来高级而过度工具化。

H8引用文件带完整路径

只写文件名 → AI 要搜索确认多次。用 @src/config/config.go 这类直接定位，省一整条搜索链路。

H9意图一次说完

四轮挤牙膏来回 = 重新组装上下文 + 历史 + 状态确认，成本是完整表达的好几倍。把背景、期望、验收条件都写清楚。

03

模型路由：别让贵模型干便宜活

路由是“匹配优先”，不是“便宜优先”。所有环节默认最强模型，就是直接烧钱。

任务推荐档位理由
写单元测试便宜模型模式稳定、模板化
写 commit message便宜模型输出短、风险低
Code Review中高档需要语义理解
架构设计强模型长链路推理
复杂 Bug 分析强模型多步假设与验证
大批量分类 / 摘要低价或 Batch规模大、成本敏感

级联升级：先便宜，再升级

便宜模型先跑
↓　判断复杂度
需要才升级
分类 → 初筛 → 摘要（20 页 → 1 页）→ 强模型推理

调预算旋钮，不只换模型

  • reasoning effort — OpenAI 建议多从 low 起步
  • thinking budget — Gemini 可压到 0，关闭思考
  • verbosity / max output tokens — 管回答长度
  • 高推理档位做分类/摘要/提交说明 = 拿推土机扫地

把路由固化成系统

Skill / Agent / Command 头部声明模型：
model: deepseek-v4-pro，context: fork。
团队每个人用 /commit、/gen-ut 都默认便宜模型，成本治理从“靠人记得切”变成“系统默认更省”。

04

上下文压缩：把高频内容压下来

四个工具方向不同、可以叠加。装上一个就能看到收益。

工具压缩什么典型节省安装
RTK 终端命令输出（cargo test / pytest / git diff…） 80–99.6% brew install rtk
Caveman AI 回复输出（删废话，A→B→C） 65–75% install.sh
headroom 所有进上下文的内容，可逆压缩按需取回 47–92% pip install headroom-ai[all]
context-mode MCP / 工具返回结果 + 跨 compact 会话连续性 98%（工具输出） npm -g context-mode

RTK — 终端输出才是 Token 大杀手

30 分钟开发会话实测：不用 RTK ≈ 118,000 token，用后 ≈ 23,900（省 80%）。

  • 测试输出 −90%、git 类 −60~80%、read/cat −70%
  • 四层策略：智能过滤 / 分组聚合 / 智能截断 / 去重合并（「连接超时 ×10」）

Caveman — 压 AI 输出端废话

四种模式：lite → full → ultra → wenyan。实测解释 React bug：118 → 15 tokens（−87%）。

  • 操作：/caveman 激活，stop caveman 关闭
  • 来源：arXiv:2604.00025

Prompt Cache：所有优化的地基

缓存的是“稳定前缀的处理结果”，不是答案。三个推论：

  • 省的不是首次，而是重复成本 — 第二次、第三次复用才体现
  • 缓存不是“写短”，是“写稳” — 天天改 System Prompt，缓存永远不命中
  • 静态放前，动态放后 — 缓存认前缀，不认任意位置的拼图
05

代码图谱：AI 不再盲搜

真正贵的不是“读代码”，而是“找代码”。图谱让 AI 在读文件之前就知道该读哪里。

GraphifyCodeGraph
形态Skill 形态，零配置MCP Server + 持久化图库（Neo4j / KuzuDB）
适用个人项目、快速上手团队、大型仓库、持久化查询
核心能力/graphify 生成知识图谱 + graph.jsontrace 调用路径 / impact 影响分析 / context 入口点
效益减少 71.5× Token（官方）平均 −47% Token、−58% Tool Call、−22% 耗时

Graphify：查询式知识地图

Tree-sitter 解析构建图谱，AI 查 graph.json 而不是反复 grep。跨文件问题时影响分析稳定得多：中间件链、Prisma model、测试文件一次列全。

CodeGraph：图数据库基准

7 个真实开源仓库（VS Code / Django / Tokio…）平均 −16% 成本、−47% Token、−58% Tool Call。收益与项目规模、语言强相关：Rust / TS 大型项目收益最显著。

06

多 Agent 协作：别让所有任务挤进一个上下文

单个 Agent 越用越贵：规划、写码、测试、Review 全在一个会话，历史越积越长，便宜活也用贵模型。

01

subagent：任务隔离的最低成本

子任务分发成独立上下文，每个 subagent 只看自己需要的，主 session 只见结果。子任务真的能拆才拆，否则更贵。

独立上下文只回传结果
02

Orchestrator–Worker

协调器只负责规划调度，不亲自读文件；每个 Worker 只做一件事，只看自己需要的上下文，完成即销毁。

每轮成本 5–10×压缩
03

上下文隔离后，数据靠文件流转

会话历史不互通，文件系统共享 → 结构化 JSON 传递（.agent/findings.json），进度文件追踪（progress.json），Worker 指令包含精确 context 裁剪。

JSON 外置记忆不做历史回放
04

并行执行：时间与成本同压

独立子任务同时启动，不等待。4 个 Worker 实际加速 2.8–3.4×；只共享进度文件，无上下文重叠。

4 Worker≈3.4× 加速

端到端对比：单 Agent vs 编排

// 单 Agent 跑 10 轮，每轮 150K+ 历史
总成本 ≈ 800K – 1.2M tokens

// Orchestrator,Worker 分工（规划、分析、实现、补测、汇总）
总成本 ≈ 100K – 150K tokens  节省 70–85%

来源差异：Worker 只看当前步骤相关内容 · 便宜模型干执行活 · 并行减少时间 · 进度文件替代历史
07

误区：很多“优化”其实在加成本

上下文越多越好

噪声越多，模型越易分神。看该读哪个文件，比读多少更重要。

MCP 越多越强

低频工具长期挂载，贡献的更多是选择成本与错误率。

全 Agent 都上最强模型

这不叫优化质量，叫放弃路由。

聊天记录当长期记忆

会话越来，关键信息越难提取，成本越高。外置才是记忆系统。

只看单价不看总成本

便宜模型如果带来更多重试、搜索、回填，总成本未必更低。

Prompt 越短越好

压缩弄丢了必要 few-shot / 格式说明 → 反复重试。要精准，不是一味缩短。

一句话结论

AI 成本优化，本质不是让你少问一句话，
而是让系统少重复做无效工作 ——

更低成本 = 更少重复上下文
            + 更合理模型路由
            + 更精准代码检索
            + 更清晰 Agent 分工
